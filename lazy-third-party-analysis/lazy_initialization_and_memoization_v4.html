Lazy initialization and memoization

When we talk about laziness, we often conflate two related but ultimately distinct features: lazy initialization and memoization.

Lazy initialization and memoization use the same underlying mechanism: compute a delayed value and retain an outcome. The categories discussed in this document are common policy bundles rather than fundamentally different mechanisms, distinguished by how many initializers may execute, how results are published, whether failure is terminal, and how recursion behaves.

Lazy initialization is a property of storage: fields, array elements, or similar locations. It avoids computing or storing a value when the storage is created, and is typically useful for reducing startup work by breaking initialization chains and delaying initialization until the value is needed, if it is needed at all.

Memoization, by contrast, is a property of methods, or more generally of computations. It speeds up a computation by remembering a value computed at an earlier time. Functional languages and techniques such as dynamic programming rely heavily on memoization as a way to improve peak performance.

The distinction becomes important under failure, recursion, and concurrency. In an execution where initialization and computation are race-free and failure-free, the two can look nearly interchangeable.

Terms

This document uses three semantic categories:

  • Lazy initialization models variable initialization. Initialization is an event that happens once: one attempt either establishes the value or establishes a terminal failure. The initializer must therefore not run concurrently or be retried after failure, and recursive initialization must be detected or otherwise handled by the initialization protocol. Lazy initialization should be used when repeated execution could invoke user or provider code again, duplicate external actions, create or leak resources, introduce races, or otherwise change observable behavior.

  • Strong memoization models a repeatable computation that establishes one result. Several attempts may execute, including concurrently, but one successful value wins and racing callers observe that winner rather than their losing candidates. Failure does not have to be terminal: a failed attempt may leave the cache empty and allow a later retry. That said, sticky failures can still be modelled on top (e.g. using an Either type) without changing the winner-selection semantics. Recursion can generally behave like ordinary recursive method execution.

  • Weak memoization models a repeatable computation for which winner selection is unnecessary. Several attempts may execute and distinct successful values may escape to different callers. A failure normally affects only its own attempt and can be retried. As before, recursion can again behave like ordinary recursive method execution.

Laziness in Java

Java and the JDK already provide several mechanisms with lazy-initialization or memoization semantics. This section first examines those mechanisms using the semantic categories introduced above, then applies the same classification to an inventory of lazy use sites across all JDK modules.

Lazy features & APIs

Java's built-in class and interface initialization is the clearest lazy-initialization mechanism. The JVM serializes initialization, executes the class initializer once, records an erroneous state after failure, and coordinates recursive requests. The initialization-on-demand holder idiom inherits these semantics. LazyConstant provides the same model for an individual value: its computing function executes at most once, success and failure are terminal, and recursive access is rejected. List.ofLazy , Map.ofLazy , and Set.ofLazy apply that policy independently to collection elements.

Dynamically-computed constants ( condy ) are examples of strong memoization. Several threads may invoke the bootstrap method concurrently; the JVM chooses one result, installs it for all threads, and ignores losing results. Successful and failed resolution outcomes are subsequently remembered without re-executing the bootstrap method. Sticky failure makes condy look initialization-like, but concurrent bootstrap execution means that it should only be used with initializers designed to run more than once.

ClassValue is another direct example of strong memoization. computeValue may run more than once under a race, but one value is associated with a class and returned. A failed computation leaves no association and may be retried. ConcurrentHashMap.computeIfAbsent reaches the same publication result by serializing computation for an absent key; failure or a null result leaves the mapping absent. The general Map.computeIfAbsent operation specifies memoization but deliberately leaves concurrency and atomicity to the map implementation.

Weak memoization is normally written as an ordinary racy field or array cache. The Classfile API contains several concrete examples. For instance, InvokeDynamicEntryImpl.asSymbol reads an @Stable field, computes a descriptor when it is absent, and returns its own stored candidate. Racing callers may therefore receive distinct but equivalent descriptors.

@Stable strongly favors one winner. Its lifecycle contract says that a properly used stable variable is set once to a permanent non-default value, after which the VM may treat that value as a constant. Observing several historical values can otherwise produce different behavior in interpreted and compiled code. The annotation does not itself provide synchronization or winner selection, so the surrounding protocol must normally use a lock, CAS, or an already canonical value to honor that contract. The documentation permits weak benign races only as a rare exception, when every value that the VM might capture is interchangeable and the use site explicitly accounts for that behavior.

Lazy use-sites in the JDK

At the time of writing, our analysis of JDK sites using lazy idioms identified 145 scalar caches. By scalar cache we mean a cache that publishes a single object, even when that object is a fully populated array, list, or map. Each site was classified using the decision graph above.

Of the 145 scalar caches:

  • 24 (16.6%) require lazy initialization;

  • 42 (29.0%) require strong memoization; and

  • 79 (54.5%) permit weak memoization.

Of the 24 scalar lazy-initialization sites, 22 are static. Although the decision graph records the minimum semantics required by each site, all 145 sites are compatible with lazy-initialization semantics.

Lazy use-sites in third-party code

To test whether the JDK observations generalize beyond the JDK, we applied the same decision graph to production code in ten prominent Java libraries and frameworks. The unit of analysis is again a scalar cache: one accessor-field publication protocol, even if the published object is a fully populated collection. Fields initialized together as one transaction count as one protocol; independent accessors count separately.

This is a balanced, manually audited sample rather than an exhaustive ecosystem census. We selected at most 15 distinct protocols per project, stratified across packages and implementation mechanisms, so that large frameworks would not dominate the result. Tests, benchmarks, generated sources, per-key caches, eager constants, and compatibility copies were excluded. Compatibility with LazyConstant

Of the 81 memoization sites, 69 (85.2%) are compatible with stronger lazy-initialization semantics: their initializer does not fail under ordinary operation, or any failure is determined by immutable input. The remaining 12 rely on a potentially transient failure being retried. They comprise two Guava arbitrary-supplier sites, SLF4J's provider-supplied MDC adapter, five JUnit dynamic class or method lookups, one Mockito security-sensitive reflective lookup, one Netty event-loop lookup that can succeed after channel registration, and two Spring Expression Language constant computations subject to per-evaluation operation limits. Converting those sites to sticky failure would change observable behavior. As in the JDK analysis, catastrophic failures such as OutOfMemoryError are outside this compatibility judgment.

Only 6 of the 35 true lazy-initialization sites (17.1%) are static, compared with 22 of 24 in the JDK inventory. The third-party sample's instance sites often guard a resource, extension, bean, connection, or application context, whereas several static holder idioms merely cache stateless, interchangeable helpers and therefore classify as memoization. Because the third-party study is balanced rather than exhaustive, this contrast is evidence about the kinds of use sites found outside the JDK, not a population-frequency estimate.

What do other languages do?

Some languages and platforms expose a direct choice between single-execution and publication-style policies. Kotlin's lazy supports several LazyThreadSafetyMode values. SYNCHRONIZED permits only one thread to execute initialization at a time, while PUBLICATION may evaluate the initializer concurrently but publishes only one result, making it a direct example of strong memoization. NONE provides no thread-safety guarantee and is intended for confined use.

C# exposes a similar choice through Lazy<T> and LazyThreadSafetyMode . ExecutionAndPublication serializes initialization and, when a value factory is used, remembers failure. PublicationOnly permits multiple threads to initialize but publishes one successful result and does not cache exceptions. These modes closely match lazy initialization and strong memoization, respectively. The None mode again assumes that synchronization is unnecessary or provided externally.

The non-thread-safe modes provided by Kotlin and C# do not offer safe weak-memoization semantics under concurrent access. Misuse has caused failures in both Kotlin and C# , illustrating that a weaker mode is easy to misunderstand.

Clojure provides separate constructs rather than modes of one abstraction: delay represents delayed evaluation, while memoize and core.memoize cache function results. Other languages provide core support primarily for one-time or serialized initialization: Rust has LazyLock and OnceLock , C++ has thread-safe function-local static initialization and std::call_once , Scala has lazy val , and Go has sync.Once and sync.OnceValue .

The terminology used by these facilities is less consistent than their underlying choices. Some serialize evaluation, some allow competing evaluations followed by winner selection, and their failure policies vary independently. Publication-style modes are nevertheless consistently strong memoization rather than weak memoization: losing computations may run, but losing values do not become the established result.

Facilities oriented toward one policy also attract requests for the other. Guava's Suppliers.memoize is memoization-oriented, but users have requested sticky failure . Go's sync.Once and OnceValue are single-execution-oriented, but users have requested retry-on-error behavior . This reinforces that execution, publication, and failure are distinct policy choices even when an API presents them as one feature.

Performance

The performance cost of a lazy computation can come from several sources:

  • Slow-path performance : the first access must run the initializer and publish its outcome, while also handling races, failure, and possibly recursion.

  • Fast-path performance : subsequent accesses must determine that initialization has completed and retrieve the cached result.

  • Extra data structures : an implementation may require wrappers, computing functions, state markers, recorded failures, or dedicated synchronization objects.

  • Synchronization : locks, CAS operations, and the associated memory-ordering constraints add work and may introduce contention.

For example, lazy initialization has stronger semantics and is therefore likely to require more state, including a lock or equivalent synchronization object. Its initializer typically runs under mutual exclusion so that no competing attempt can execute concurrently. Memoization has fewer requirements: strong memoization can use CAS to select one result from competing computations, while weak memoization can use plain reads and writes without selecting a winner.

It is relatively easy to measure each of these costs in synthetic benchmarks. However, assessing the impact they have in real-world usage is a different, more complex matter, and one that we will discuss in the remainder of this section.

We identified 38 cache sites in the Classfile API with the same general shape: an accessor computes a value on first use, stores it in a field, and returns the cached value thereafter. The sites include constant-pool entry lookups in bound instructions, class and member attributes, and class-reader metadata. Using mainline as the baseline, we instrumented all 38 sites in four different ways:

  1. LazyConstant . Replace each cache site with a LazyConstant whose computing function contains the original accessor body.

  2. LazyConstant + condenser . Same as (1), but in combination with a jlink -time condenser that lowers each suitable LazyConstant caching site into corresponding fields and initialization logic. This removes the wrapper and captured computing function, but each condensed constant still requires some ad-hoc state management.

  3. Strong cached methods . Replace each caching site with a cached method whose backend uses CAS to select one winning result.

  4. Weak cached methods . Same as (3), but with a cached-method backend that uses plain reads and writes.

We then used three Classfile API benchmarks representative of different workloads:

  • Shallow traversal collects class, method, and field names while inflating as little of the model as possible.

  • Deep traversal also examines opcodes, attributes, and other details.

  • Repeated deep traversal keeps walking an already-inflated model, representing a workload which performs substantial repeated work.

Standalone LazyConstant is too slow for these cache sites, largely because it allocates several objects per site. This is consistent with its intended use: a single constant is normally accessed many times, amortizing its representation and initialization costs. The Classfile API has a different kind of laziness where many of its cached values are only accessed once (if ever). The condenser largely makes up the gap by removing that representation overhead. Cached methods also perform well, and there is no material difference between the publication policies measured here.

This benchmark also shows why assessing each cost in isolation can be misleading. A repeated deep traversal naturally has many more cache hits, but parts of the model are still inflated on demand: CodeModel.elementList() materializes fresh bound instruction objects on each traversal. Construction and slow-path costs therefore bleed into repeated access too, and the benchmark measures the end-to-end cost that an API client sees rather than only the fast path of already-initialized caches.

Conclusions

What is generally referred to as "laziness" is a spectrum of possible policies. This document focuses on three common bundles: lazy initialization, strong memoization, and weak memoization. Strong and weak memoization differ only in their publication semantics: strong memoization selects one established value, while weak memoization does not. Lazy initialization additionally constrains initializer execution, failure handling, and recursion.

Does this mean we need three distinct features? A use site can often be compatibly upgraded to stronger semantics -- in fact, all 145 scalar sites analyzed in this document are compatible with lazy-initialization semantics. There are, however, no free lunches: while a memoization site might be semantically compatible with lazy initialization, some costs associated with the stronger semantics might be unacceptable -- as the Classfile API experiment clearly shows.

There are three plausible approaches. We can continue to unroll performance-sensitive caches by hand, accepting the associated boilerplate. Alternatively, we can stretch LazyConstant to handle such caches with a link-time condenser, retaining the API while removing the per-site representation cost. Or we can treat memoization as a separate use case and provide a feature designed for it. Given the relative incidence of memoization vs. lazy initialization, and much more direct syntax provided by a true language feature such as cached methods, this might well be the more honest approach.

It might also be tempting to go the other way, and stretch cached methods to cover lazy initialization cases. However, sticky failure needs an explicit result representation such as Either , while at-most-once execution needs mutual exclusion around the initializer. While doable, this adds considerable ceremony and would quickly invite additional knobs on cached methods (like Kotlin has done), which could dilute the feature's semantic crispness and make it more confusing.

Moreover, if cached methods are pursued, our analysis shows there is little reason for them to provide a weak variant. As we have explained, a weak-memoization site can always use strong memoization, and the Classfile API experiment found no meaningful performance difference between CAS and plain publication. Cached methods should therefore provide strong winner selection and retry-on-failure semantics. This, in turn, allows cached methods to benefit from the constant-folding semantics enabled by @Stable .

Finally, since most scalar lazy-initialization sites are static, a lazy static feature might also serve many of those sites, either alongside LazyConstant or as an alternative for static values. That said, lazy static would only work in static contexts, and some uses of LazyConstant might still come in handy for replacing brittle, hand-written double-checked-locking idioms.
