# Applicability of `Lazy` in the JDK and open-source Java software

**Architecture review, 14 October 2026.** This report evaluates the preview prototype in branch `prototype/lazy-one-class` at commit `615d99c8578f80cba9883d5428f01485b04d84b4`. The contract assessed is [`java.lang.util.Lazy`](src/java.base/share/classes/java/lang/util/Lazy.java), with [`Lazy.md`](Lazy.md) as its design record. This is a source-level applicability study, not a proposal to migrate the cited projects or a performance benchmark. The prototype is not a committed Java platform API.

## Executive assessment

`Lazy` addresses two distinct and recurrent patterns: a cache owns independently initialized state, whereas an updater initializes a caller-owned location. The latter is particularly useful where a receiver already has a nullable field or a fixed array slot and an extra holder would be undesirable. `SERIALIZED` matches double-checked, retry-on-failure initialization; `PUBLISH_ONCE` matches repeatable computations whose losers can be discarded; `PLAIN` matches intentionally uncoordinated memoization. The owned-storage collection forms express fixed index, key, and membership universes, including cached `false` set memberships that a primitive updater cannot store in its reserved `false` state.

The boundary is as important as the positive cases. Many widely used “lazy” implementations are open-ended maps, refreshable registries, asynchronous signal caches, or closeable resources. Replacing these with `Lazy` would change their contract. A high-quality adoption argument should present these exclusions explicitly. Source examples below are pinned to repository commits; the tables count one representative site per external project, not all lazy sites in that project.

Of the **90 selected source sites**, **22 are direct fits**, **38 are conditional**, and **30 have no direct fit**. Among the 60 plausible sites, **50 primarily use an updater**, including **44 field updaters**; the fixed-key map cache and structured-segment updater have no positive example in this sample. These figures measure the audited sites, not the prevalence of lazy patterns across the projects.

## Capability matrix

| `Lazy` construct | Storage and granularity | Coordination/failure choice | Main source pattern | Hard boundary |
| --- | --- | --- | --- | --- |
| `ofScalarCache(Supplier)` | One value in a returned supplier | `COMPUTE_ONCE` by default; `PUBLISH_ONCE` explicitly | Static or instance one-time non-null object | Extra holder; no invalidation or close protocol; `COMPUTE_ONCE` retains failures |
| `ofScalarCache(CacheMode, Function)` | One value in a returned function, **not one per context** | Both cache modes | Noncapturing computation with an access-time receiver or first-caller context | All non-null contexts share one retained winner, which the application must accept; a null context throws even after initialization |
| `ofListCache` | One value per index in a fixed-size unmodifiable list | Both cache modes, independently per index | Indexed tables, fixed slots | No resizing, mutation, null element, or access-time callback |
| `ofMapCache` | One value per copied key in an unmodifiable fixed-key map | Both cache modes, independently per key | Known finite key universe | No new keys, eviction, invalidation, or null value |
| `ofSetCache` | One Boolean membership per copied candidate | Both cache modes, independently per candidate | Deferred predicate over a known candidate set | No new candidates or mutable membership; traversal may evaluate candidates |
| Static/instance field updater | One caller-owned field, optionally per receiver | `PUBLISH_ONCE`, `SERIALIZED`, or `PLAIN` through builder; conveniences fix `PUBLISH_ONCE` | Nullable field sentinel, double-checked singleton, holder-free per-object memo | Default value reserved; no direct reset or unmanaged writes; private fields need suitable lookup/module access; `SERIALIZED` has auxiliary coordination state |
| Direct or field-backed array updater | One caller-owned physical element; any positive rank up to method/array limits | Three updater modes | Fixed slot table, multi-dimensional result array | No default-valued result; no replacement of array path while in use; `PUBLISH_ONCE` discards losing candidates |
| Memory-segment updater | One caller-owned value selected by layout path; zero-bit pattern is the uninitialized sentinel | `PUBLISH_ONCE` or `PLAIN`; no `SERIALIZED` | Fixed structured segment location | Segment lifetime is external; atomic access/alignment constraints; no dereference path |
| `buildUseSite` updater | Same selected location as declaration-site updater; callback supplied on each call | Chosen updater mode | Access-specific computation with fixed coordinates | Every call supplies a non-null callback, even after initialization; callbacks sharing one location should be interchangeable; no public use-site cache equivalent |

For caches, `COMPUTE_ONCE` invokes a computation at most once per location and makes failure sticky; a non-`Error` failure is reported through `NoSuchElementException`, while an initial `Error` is thrown directly and subsequent access reports `InitializationError`. The original throwable is not retained. Cache `PUBLISH_ONCE` can compute concurrently, installs one winner, and retries after failure. Updater `SERIALIZED` also allows retry after failure, while excluding concurrent computation for the same physical location. Updater `PUBLISH_ONCE` may compute duplicate candidates and returns the installed winner on success. A racing call whose computation fails still fails, even if a different call publishes a value. Updater `PLAIN` can overwrite a competitor and supplies no safe-publication guarantee. Cache values must be non-null. Updaters reserve `null`, `false`, integral zero, positive floating-point zero, or a segment value's zero-bit pattern to mean uninitialized; negative floating-point zero and NaN are valid. A reserved result cannot be stored without a non-default wrapper. Null-restricted reference fields and arrays cannot use this sentinel: the former are rejected when the updater is created, and access to an element of the latter fails even if it already holds a value. These distinctions, rather than the word “lazy,” determine the row assessments.

The updater builder defaults to a public lookup; private fields require authorized lookup/module access, supplied explicitly to the builder or obtained for the caller by a caller-sensitive convenience factory. Rank-two and higher Java-array coordinates, array-valued fields, and primitive carriers beyond the ready-made `int` and `long` forms require custom functional-interface shapes. Cache storage strongly retains its computed values; it retains each computing function until all locations have succeeded or recorded permanent failures. Returned cache suppliers, functions, and collections are deliberately not `Serializable`. Both fixed-key and fixed-candidate factories copy their input universe, which may traverse a lazy input set and compute its memberships. Computation uses the retained key or candidate, which can matter if an equal lookup object has distinct identity or if key state changes.

### Versatility measures

The report uses four measures rather than a single unexplained score:

1. **Source-site fit:** direct, conditional, or no direct fit, with denominators of 20 JDK sites, 50 library sites, and 20 application sites.
2. **Construct reach:** the number of direct and conditional sites whose *primary* mapped construct is each cache or updater shape. Each row contributes to at most one primary shape; no-fit rows do not count as coverage.
3. **Policy reach:** which of `COMPUTE_ONCE`, cache/updater `PUBLISH_ONCE`, `SERIALIZED`, and `PLAIN` are needed by the direct/conditional examples.
4. **Uncovered dimensions:** one primary reason per no-direct-fit site, with secondary conditions preserved in its assessment. This makes the blocker table additive without pretending each mismatch has only one cause.

The metrics are architectural breadth indicators. They do not estimate throughput, allocation savings, latency, or the number of sites in a full repository. In particular, an updater removes the need for an extra *per-receiver* cache holder, but the amount saved depends on the application's object graph and the updater's own coordination costs.

## Architectural reading of the source evidence

The most persuasive use is a **caller-owned field that uses `null` as its uninitialized sentinel and requires a non-null initialized value**. [FontManagerFactory](src/java.desktop/share/classes/sun/font/FontManagerFactory.java#L44) and [JdkXmlConfig](src/java.xml/share/classes/jdk/xml/internal/JdkXmlConfig.java#L77) illustrate serialized singleton construction; [Spring Security's service](https://github.com/spring-projects/spring-security/blob/ab9c14c12f9503817b08c3253572a51dfbe2f09c/oauth2/oauth2-core/src/main/java/org/springframework/security/oauth2/core/converter/ClaimConversionService.java#L47), [OpenTelemetry's component name](https://github.com/open-telemetry/opentelemetry-java/blob/4662b0806c95856a7cb86ca765960f09241bdec2/sdk/common/src/main/java/io/opentelemetry/sdk/common/internal/ComponentId.java#L45), and [gRPC's marshalled bytes](https://github.com/grpc/grpc-java/blob/6f5fccee9f0946632a2ed1e7c37657a423a22a95/api/src/main/java/io/grpc/Metadata.java#L938) show the same shape in libraries. The distinction from `COMPUTE_ONCE` is material: all of these retry after a failed computation, whereas that cache mode records failure permanently. A `SERIALIZED` updater keeps the existing field and models the retry, subject to its separate per-location coordinator and recursion semantics. An existing `synchronized(this)` can also serialize *other* operations or fields; [Keycloak's two lazy fields](https://github.com/keycloak/keycloak/blob/867100dda9ffa8149fbbe213120de16f18d0483d/services/src/main/java/org/keycloak/credential/WebAuthnCredentialProviderFactory.java#L39) illustrate why monitor identity sometimes needs review.

An updater can also initialize a **mutable container as one value** while leaving later content changes to the container's ordinary API. [Jenkins `Actionable`](https://github.com/jenkinsci/jenkins/blob/1e6ac398bcf318c50493ce5e0e3687b86fc91e3b/core/src/main/java/hudson/model/Actionable.java#L88), [Hadoop `Configuration`](https://github.com/apache/hadoop/blob/f41bb2ebdcf86937c7b732dec40dba48ddb40700/hadoop-common-project/hadoop-common/src/main/java/org/apache/hadoop/conf/Configuration.java#L4061), and [Maven's lazy map delegate](https://github.com/apache/maven/blob/f4ddd1829d4aaac468db9e643796614da9a1b55b/impl/maven-core/src/main/java/org/apache/maven/project/DefaultProjectBuilder.java#L1362) illustrate this. They are field-updater cases, not uses of `ofMapCache` or `ofListCache`, whose returned collections are unmodifiable and have fixed universes.

The best replacement need not have the same surface shape as the current code. [Druid's memoized regex](https://github.com/apache/druid/blob/7c89096bd1faefb14a4efef1cbd684719bf2aa83/processing/src/main/java/org/apache/druid/data/input/impl/RegexInputFormat.java#L63) and [Trino's memoized output types](https://github.com/trinodb/trino/blob/2896467bf3a1e3397851763be4806f1e9211baf0/core/trino-main/src/main/java/io/trino/sql/planner/PartitioningScheme.java#L100) use Guava suppliers. `COMPUTE_ONCE` would make an exception sticky, unlike Guava's retry. Replacing a private supplier field with a nullable result field and a `SERIALIZED` updater preserves one-at-a-time computation and retry. Druid must read its mutable regex configuration on each attempt until initialization succeeds; both projects must preserve their existing JSON treatment of the cache.

The **publication-only** shape is also real. [Protocol Buffers' descriptor retriever](https://github.com/protocolbuffers/protobuf/blob/369cb767b2b87574318a8a52080b7148964a0877/java/core/src/main/java/com/google/protobuf/GeneratedMessage.java#L1931-L1948) loads before installing a descriptor in a volatile field, allowing competing loads. A `PUBLISH_ONCE` field updater expresses the installed winner. Fixed indexed storage is narrower: [ImageTypeSpecifier](src/java.desktop/share/classes/javax/imageio/ImageTypeSpecifier.java#L1108) and [XSModelImpl](src/java.xml/share/classes/com/sun/org/apache/xerces/internal/impl/xs/XSModelImpl.java#L390) are candidates, but their current racy-return or whole-object locking details require explicit validation. The one strong **candidate-membership** example, [HandshakeContext](src/java.base/share/classes/sun/security/ssl/HandshakeContext.java#L560), has a finite `NamedGroupSpec` universe and needs to remember both `true` and `false`; `ofSetCache` represents that without an extra sentinel.

**Computation placement is a separate axis from storage shape.** [JdkXmlConfig](src/java.xml/share/classes/jdk/xml/internal/JdkXmlConfig.java#L77) uses the first successful initializer's `stax` flag, and [Hibernate's collection persister](https://github.com/hibernate/hibernate-orm/blob/fb96aa70f0ad716643992c8b56fa5d62bf6cd135/hibernate-core/src/main/java/org/hibernate/type/CollectionType.java#L295-L313) uses the first successful caller's session factory. A use-site updater can accept that input without retaining a capturing lambda in each holder; callers still supply a non-null function on every access, which may itself allocate. [JShell's `Startup`](src/jdk.jshell/share/classes/jdk/internal/jshell/tool/Startup.java#L352) instead has a fixed enum key set but takes an access-time `MessageHandler`; its current map cannot become `ofMapCache` with that callback. A fixed array plus a use-site updater preserves the behavior after a private representation change. This distinction prevents the fixed-key collection factories from being mistaken for general `computeIfAbsent` replacements.

**Sentinels and return semantics limit mechanical substitution.** The updater's default-valued state excludes primitive zero/false and reference `null` as successful stored results. A non-default wrapper can represent a logical default, but may add allocations and change serialization or API types. [Gradle's nullable `AtomicLazy`](https://github.com/gradle/gradle/blob/6366fe02df691692f7681d3ba66cb5e7283fc969/platforms/core-runtime/functional/src/main/java/org/gradle/internal/lazy/AtomicLazy.java#L39) is a direct scalar-cache fit only with such an internal box or `Optional<T>`. [ZipPath](src/jdk.zipfs/share/classes/jdk/nio/zipfs/ZipPath.java#L630) is an especially cautionary example: a boxed scalar cache can retain hash zero, yet the source can retain a mutable caller byte array, and the current zero sentinel can trigger recomputation. A permanent scalar cache changes that edge behavior. Even with non-default values, `PLAIN` returns the invoking thread's own candidate; source code that writes and then rereads a field or array slot can return another thread's later candidate. Rows with that pattern are conditional unless the final reread is retained or the race behavior is explicitly judged irrelevant.

**Lifetime remains outside `Lazy`.** [FileInputStream](src/java.base/share/classes/java/io/FileInputStream.java#L544), [ModulePatcher](src/java.base/share/classes/jdk/internal/module/ModulePatcher.java#L282), and [HikariCP](https://github.com/brettwooldridge/HikariCP/blob/a4d93f4f85517f90e632b795486d7102e933d7ff/src/main/java/com/zaxxer/hikari/HikariDataSource.java#L92) have a close-versus-initialize protocol and, in some cases, checked exceptions. `Lazy` has no public close-aware location state. A `PUBLISH_ONCE` computation may also discard a resource produced by a losing thread. Likewise, open-ended, mutable key registries such as [Caffeine's manual cache](https://github.com/ben-manes/caffeine/blob/6bfe815f0f6a2daba967385d02c52890c33d8142/caffeine/src/main/java/com/github/benmanes/caffeine/cache/LocalManualCache.java#L62) and asynchronous signal caches such as [Reactor's `MonoCacheTime`](https://github.com/reactor/reactor-core/blob/0d1a22ce5b31e4f2a4b9d2c6b29f943fcb6f2034/reactor-core/src/main/java/reactor/core/publisher/MonoCacheTime.java#L123) need different state machines. These exclusions should remain visible when presenting the API's scope.

## Implications for API review

1. **Keep the cache/updater distinction explicit.** The source examples do not justify treating the modes as interchangeable. The same synchronized lazy field can require retry after failure, while an owned cache's `COMPUTE_ONCE` deliberately makes failure sticky. The two storage families also differ in whether an extra holder is allocated, whether a default value is valid, and who controls location lifetime.
2. **Retain both declaration-site and use-site updater computation.** First-caller parameters and diagnostics appear in actual JDK and library sources. The use-site form needs a clear compatibility rule for functions sharing one physical location. It should not imply one cache entry per function or per context.
3. **Describe `PLAIN` as a migration tool only for deliberately racy code.** Its own-result return and lack of safe publication can differ from both a final source-field reread and CAS publication. The branch's acquire/release cache guarantees should not be imputed to this updater mode.
4. **Keep fixed-universe collections narrowly framed.** A lazy map copies its key universe; a lazy set copies its candidate universe. Ordinary `computeIfAbsent` registries, eviction, reset, and mutable collections should not be counted as fits merely because they initialize on demand. Lazy input sets may themselves evaluate memberships while the universe is copied, and computation uses the retained key or candidate rather than necessarily the equal object used for lookup.
5. **Do not infer performance from fit counts.** The most relevant measurements are allocation per holder, steady-state access latency, contention and losing-computation cost, `SERIALIZED` coordination footprint, and bootstrap footprint. [MethodHandleImpl](src/java.base/share/classes/java/lang/invoke/MethodHandleImpl.java#L84) is a particularly sensitive integration test because updater construction itself enters method-handle and classfile machinery; boot, CDS, and AOT tests are necessary before calling that site usable.
